# 다른 SmartHome-Bench 영상 검증 (2026-11-17)

브랜치: `codex/video-sequence-aggregate-tests` (`origin/main`의 `65fb0f7`에서 분기). 아래 표는 수정 전 최초 측정값이다.

## 범위와 방법

- `0188`, `0518`을 제외한 `0065`, `0142`, `0608`, `0642`, `0936`을 확인했다.
- 시퀀스는 DB의 실제 `behavior_events`를 **읽기 전용**으로 가져와 현재 브랜치의 `run_sequence_query`에 전달했다. API와 화면 결과는 아니다. `top_k=10`을 사용했다.
- 집계는 저장된 `new-pipeline/*-result.json`의 검증 응답을 현재 `reduce_transitions`와 `evaluate_case`로 재계산하고, 잠정 기준 구간과 시각을 대조했다. 저장된 모델 응답을 재사용한 오프라인 검사이며 신규 영상 분석이나 서비스 API 결과가 아니다.
- 질문 라우팅과 집계 행동 해석은 외부 서비스 호출 없이 현재 코드의 `classify_with_rules`, `parse_count_action`으로 확인했다.
- 스테이징 웹 주소는 이 실행 환경에서 DNS 조회가 실패했다. 실제 검색 경로 실행은 자동 승인 검토가 DB 이벤트/검색 결과의 외부 LLM·벡터 서비스 전송 가능성을 이유로 거부하여 수행하지 않았다.

## 이 브랜치의 수정 후 재검증

- SmartHome-Bench의 `_000_frame_...` 형식 프레임 키에서 영상 상대 시각을 복원해 `처음/마지막/이전/다음` 질문에 사용할 수 있게 했다. `내려온` 질문과 `내려옴` 이벤트 설명도 연결했다.
- `거실과 소파 사이에서`의 `사이`를 장소 이름으로 오인해 모든 이벤트를 거르던 시퀀스 필터도 수정했다. 저장 이벤트가 없는 행동까지 만들어 내지는 않는다.
- 실제 DB 이벤트로 `0065`의 `소파에서 내려온 다음` 질문을 다시 실행하면 카드 ID 114(영상 22초)가 나온다. **저장 이벤트의 다음 장면**을 찾는 오류는 해결됐지만, 원본에서 그 장면이 실제 다음 행동인지는 아직 검증되지 않았다. `0608`의 `수영장에서 나온 다음` 질문은 여전히 기준 장면을 하나로 좁히지 못한다.
- `0142`의 `밥을 먹다가 고개를 몇 번 들었어?`는 더 이상 `먹기` 횟수로 잘못 해석하지 않는다. 별도의 고개 들기 횟수 지원이 없으므로 숫자를 제시하지 않는다.
- `0936`의 앞발 질문은 모델이 `앞발 하나가 바닥에서 떨어짐`으로 바꾸지 못하도록 `두 앞발을 들고 다시 내림`, `뒷발은 바닥에 있어도 됨`, `유리문`을 전환 기준으로 고정했다. 기존 저장 결과 중 같은 기준을 사용한 실험의 후보 합집합은 8건 중 7건 확정·1건 미확정이었다. 이는 **과거 모델 실행 결과**이며 이번 변경을 새로 실행한 점수는 아니다.
- `0642`의 저장된 후보 합집합에는 5.25초 입수의 전후 근거가 확정으로 남아 있었지만 개체 추적이 `unknown`이라 최종 횟수에서 빠졌다. 별도 크롭 검토는 두 번째 강아지라고 판단했다. 그 후보에만 `animal_2`를 가정하여 현재 리듀서를 오프라인 실행하면 확정 1→2로 바뀐다. 실제 새 추적 모델이 이 식별을 할지는 아직 확인하지 않았다.
- `0065`는 후보가 있어도 전후 프레임 확인에 실패한 사례가 많다. 미확정 후보에 대해 넓은 구간 재검토와 독립 근거 확인을 추가했다. 실제 재실행 결과는 아래에 기록했다.
- 개체 추적은 이제 후보의 결과 프레임 한 장 대신 전·후 프레임을 함께 본다. 서로 다른 강아지가 가까운 시각에 같은 물에 들어가는 `0642` 사례를 겨냥한 일반적인 변경이다. 불확실한 개체는 여전히 `unknown`으로 남긴다.

## 충전 후 실영상 재검증

같은 MP4와 고정 행동 기준으로 다시 실행했다. `0936`은 0.5초 기본 탐색에 2초짜리 짧은 창의 0.25초 탐색을 추가했다. 짧은 앞발 동작을 0.5초 탐색이 놓치는지 확인하기 위한 것이다. `0065`는 전체를 0.25초 간격으로 탐색하고, 뒤쪽 진입의 독립적으로 검증된 이전 프레임을 새로운 진입의 리셋 근거로 사용했다. 파일별 모델 응답과 확정/미확정 후보는 [실행 근거](../notebooks/smarthome-bench-evidence/new-pipeline/branch-validation-2026-11-17/)에 저장했다.

| --- | ---: | ---: | --- | --- |
| `0065` | 2 | 3 | 잠정 4회 + 모호 1회. 개별 기준 시각이 없어 시각 일치율 계산 불가 | 2.75초와 21.25초 진입은 확정. 어두운 개체와 컷 때문에 나머지를 확정하지 못함. |

`0936`의 새 0.25초 전체 탐색 단독 실행은 4건, 두 전체 탐색의 후보 합집합 재검증은 3건으로 오히려 줄었다. 모델의 재검증 응답이 실행마다 달라지는 점을 확인했다. 반면 5.25~8.75초의 짧은 창 탐색이 6.25초 누락 후보를 발견했고, 이를 일반적인 짧은 창 2차 탐색으로 넣은 전체 재실행이 7건을 확정했다. 이 2차 탐색은 API 호출량과 처리 시간을 늘린다.

`0065`는 독립 프레임 검토에서 19.25초 바닥 상태와 21.25초 소파 위 상태를 같은 개체의 전환으로 확인했다. 이전 후보와의 개체 연결이 불확실하다는 이유만으로 그 새 전환을 버리던 리셋 로직을 수정하고 저장된 검증 응답을 재집계해 2건 확정했다. 3개 미확정 후보를 실제 횟수로 합산하지 않았다.

## 시퀀스 이벤트 생성의 앞단 수정

로컬 MP4에 현재 `detect_motion`을 실행하니 `0065`는 2.0~23.02초, `0642`는 4.0~7.51초, `0936`은 2.51초 한 시점만 움직임 구간으로 감지했다. 기존 `extract_frames`는 움직임 구간에서 기본 2초마다 한 프레임을 뽑고, 일부 움직임이 잡히면 구간 밖은 기본으로 전혀 뽑지 않았다. 그래서 첫 입수나 짧은 앞발 동작이 이벤트 생성에 전달되지 않는 구조였다.

이 브랜치에서는 움직임 구간 추출을 기본 1초 간격으로 높이고, 움직임 감지 밖도 기본 1초 간격으로 보조 추출한다. 보조 프레임은 움직임 구간의 앞뒤를 섞지 않고 연속된 최대 12초 창으로 묶어 VLM이 여러 시각을 함께 보게 했다. 로컬 프레임 추출 재검증에서 `0065`는 23장(0~23초), `0642`는 13장(0~14초, 보조 구간 0~2초와 9~14초를 분리), `0936`은 21장(0~21초)을 얻었다. **기존 DB 이벤트는 자동 갱신되지 않으며**, 재처리 후 새 이벤트의 정확도와 서비스 검색 결과는 아직 검증하지 않았다. 프레임 업로드·YOLO·CLIP 작업량은 종전 기본 설정보다 늘어난다.

## 재현 및 후속 우선순위

### DB·서비스 재검증 시도

사용자의 후속 요청에 따라 기존 DB를 읽기 전용으로 확인했다. `0065`는 행동 이벤트 6건·장면 11건, `0642`는 2건·8건, `0936`은 7건·12건이다. 현재 브랜치의 외부 호출 없는 순서 질문 함수에 기존 DB 이벤트를 전달하면 `0065` 전체 순서 6카드, `0642`의 분수 질문 0카드, `0936`의 유리문 질문 0카드다.

수정된 프레임 추출기를 이용해 로컬 MP4 세 편을 다시 프레임 추출하고 기본 `gpt-4o-mini` 이벤트 분석기로 새 이벤트를 생성했다. [원본 이벤트 결과](../notebooks/smarthome-bench-evidence/new-pipeline/branch-validation-2026-11-17/event-recheck/)를 보존했다.

| 영상 | 새 프레임 | 새 자동 이벤트 | 원본 대비 판단 |
| --- | ---: | ---: | --- |
| `0065` | 23 | 4 | 초반 소파 진입이 독립 이벤트로 명확히 기록되지 않음 |
| `0642` | 13 | 5 | 후반 입수는 기록했으나 첫 입수는 `앞발을 물속에 담금`으로만 표현 |
| `0936` | 21 | 3 | 앞발 들기 반복이 전혀 기록되지 않음. 같은 프레임의 `gpt-4o` 재실행은 이벤트 0건 |

따라서 **이 자동 생성 결과로는 DB 이벤트를 교체하지 않았다.** 지금 저장하면 검증된 집계 전환과 순서 답변을 오히려 잃을 수 있다. 현재 워커의 1초 프레임과 최대 6장 대표 프레임으로는 `0936`의 빠른 반복을 이벤트로 만들지 못한다. 집계 전용 전체 영상 분석은 7건을 찾았지만 이 결과는 워커의 일반 이벤트 생성 경로와 아직 연결되지 않는다.

처음에는 스테이징 웹·API 주소에 각각 브라우저 연결 실패와 DNS/연결 시간 초과가 났다. Cloud Run 서비스 주소 조회도 현재 로컬 GCP 계정에 `run.services.get` 권한이 없어 실패했다. 이후 웹 주소와 웹의 `/api/` 프록시가 HTTP 200으로 응답해 아래 검증에 이용했다. 실제 `/query` 경로 실행은 DB의 비공개 영상 이벤트가 외부 모델/벡터 서비스로 나갈 수 있다는 이유로 자동 승인 검토에서 거부됐다. 로컬 MP4 프레임 전송 승인과 별개로 DB 파생 데이터의 외부 전송 승인을 요청했다. 그 승인이 있기 전에는 해당 경로를 실행하지 않는다.

### 확정 전환의 DB 재인덱싱

집계 전용 전체 영상 검증에서 확정된 전환만 DB 행동 이벤트로 만드는 경로를 확장했다. `0642` 물속 진입과 `0936` 앞발 들기 질문을 집계 질문으로 해석하고, 각 확정 전환을 짧은 독립 구간으로 저장한다. 같은 검증 창이 겹쳐도 서로 다른 빠른 반복이 하나로 합쳐지지 않는다. 기존 자동 이벤트 대신 검증 결과를 메모리에서 대입한 시퀀스 시험은 `0642` 0→2카드, `0936` 0→7카드였다. 전체 277개 테스트가 통과했다.

읽기 전용 계획에서 `0642`의 기존 입수 이벤트 ID 128 한 건을 3.0·5.0초 전환 두 건으로, `0936`의 기존 앞발 이벤트 ID 133~139 일곱 건을 2.0·4.5·6.25·7.75·9.5·15.5·19.25초 전환 일곱 건으로 교체하기로 확인했다. 기존 이벤트를 각각 `/private/tmp/smartbench_0642-behavior-backup-2026-11-17.json`, `/private/tmp/smartbench_0936-behavior-backup-2026-11-17.json`에 백업하고 트랜잭션으로 갱신했다. 갱신 후 DB를 다시 읽어 같은 시퀀스 질문을 실행하면 각각 **2카드와 7카드**가 해당 시각으로 반환된다. `0936` 영상 시작 경계의 미확정 두 후보는 저장하지 않았다. `0065`는 2건만 확정된 상태여서 DB를 바꾸지 않았다.

스테이징 웹의 `/api/health`와 `/api/openapi.json`은 HTTP 200을 반환했다. 첫-party `/api/recordings/events`에서는 `0936`의 새 앞발 이벤트가 조회됐다. 이 엔드포인트는 같은 행동 범주를 한 건으로 줄여 보여주므로 전체 7건의 증명은 DB 재조회 결과에 따른다. 이 시점에는 스테이징 `/query`의 답변과 실제 브라우저 재생 시점을 확인하지 못했다.

### 승인 후 스테이징 검색 검증

사용자가 DB 파생 데이터의 외부 전송을 명시적으로 승인한 뒤 스테이징 웹의 `/api/query`에 대상 영상의 순서·횟수 질문 여섯 개를 실행했다. 응답 요약은 `/private/tmp/kidog-video-count-2026-11-17/staging-query-2026-11-17.json`에 저장했다.

| 영상·질문 | 스테이징 응답 | 카드 시각 |
| --- | --- | --- |
| `0065` 전체 순서 | 6카드, 기존 소파 중심 설명 유지 | 2, 4, 10, 12, 16, 22초 |
| `0065` 소파 올라간 횟수 | 미지원, 수치 없음 | 없음 |
| `0642` 분수 행동 순서 | **2카드**, 두 입수 설명 | 3, 5초 |
| `0642` 분수 입수 횟수 | 미지원, 수치 없음 | 없음 |
| `0936` 유리문 행동 순서 | **7카드**, 앞발 들기 반복 설명 | 2, 4.5, 6.25, 7.75, 9.5, 15.5, 19.25초 |
| `0936` 앞발 든 횟수 | 미지원, 수치 없음 | 없음 |

횟수 질문 미지원은 스테이징이 아직 메인 배포 코드로 실행되기 때문이다. 같은 DB를 현재 브랜치의 실제 `run_rag_query`로 호출하면 `0642`는 집계 2건·카드 2개, `0936`은 집계 7건·카드 7개를 반환한다. `0065`는 2건만 확인된 상태이므로 정확한 집계 지원에 포함하지 않았다. 브라우저 재생 버튼의 실제 이동 시각은 UI 자동화 권한이 없어 아직 확인하지 못했다.

### 자동 이벤트 생성의 추가 품질 실험

`0065` 원본은 여러 카메라 화면이 전환된다. 소파 주변의 어두운 강아지를 컷 사이에서 동일 개체로 추적할 수 없는 후보가 있어, 잠정 기준 4회를 새 확정 횟수로 승격하지 않았다. `0936`에서는 기존 프롬프트의 소파 예시가 실제 유리문 영상에도 `소파`라는 잘못된 대상을 쓰게 하는 현상이 보였다. 0.25초 프레임의 중립적인 짧은 창에서는 앞발 동작을 더 찾았지만, 영상 전체 자동 이벤트 추출에서는 22건 중 중복과 잘못된 소파 이벤트가 섞였다. 따라서 촘촘한 자동 이벤트 생성 실험은 워커 기본 경로에 넣지 않았다. 위 DB의 `0642`·`0936` 이벤트는 별도로 전후 상태와 개체를 검증한 집계 결과만 사용했다.

다른 로컬 영상에도 검증 경로를 재사용할 수 있도록 `scripts/validate_video_aggregate.py`에 `--video-id`, `--query`, 선택적 `--video-path`를 추가했다. 기존 SmartHome-Bench `--ids` 호출도 유지한다. 분석 결과는 후보·전후 근거·미확정 내역을 JSON으로 남기며, DB 반영은 별도 재인덱싱 명령의 검토 후 적용 단계다. 전체 277개 테스트와 CLI 도움말 실행이 통과했다.

- `python -m unittest discover -s tests -p 'test_sequence_query.py' -q`: 36개 통과
- `python -m unittest discover -s tests -p 'test_sequence_unreviewed_eval.py' -q`: 76개 통과
- `python -m unittest discover -s tests -p 'test_evaluate_video_aggregate.py' -q`: 2개 통과
- `python -m unittest discover -s tests -p 'test_aggregate_query.py' -q`: 5개 통과
- `.venv/bin/python -m unittest discover -s tests -p 'test_video_aggregate.py' -q`: 20개 통과 (짧은 창 탐색과 독립 확인된 새 진입 리셋 포함)
- `python -m unittest discover -s tests -p 'test_frame_extractor*.py' -q`: 10개 통과
- `.venv/bin/python -m unittest discover -s tests -q`: 전체 275개 통과
- 저장된 집계 검증 응답에 `reduce_transitions`를 다시 적용한 결과는 파일의 확정/미확정 수와 모두 일치했다.

1. 시퀀스: SmartHome-Bench 프레임 키에도 재생 가능한 영상 시각을 부여해 `다음/이전` 질문이 빈 결과로 끝나지 않도록 한다. 원본과 어긋나거나 정보가 없는 DB 이벤트는 재추출·검수한다.
2. 집계: `0065`의 남은 미확정 구간을 원본과 대조한다. 지원하지 않는 행동 질문에는 근거 없는 숫자를 내지 않는다.
3. 수정 후 같은 영상·질문을 실제 API와 화면에서 다시 실행하고, 각 카드의 재생 시점이 원본 행동과 맞는지 확인한다. 브랜치를 메인에 머지하고 스테이징에서 확인하는 단계는 그다음이다.

## `0065` 사용자 검토 후 정성 답변 (2026-11-18)

사용자는 0~1초와 2.5~7초에 소파 위에 있고, 9·15·17·20초 무렵에도 짧게 올라간다고 검토했다. 빠른 움직임과 화면 전환 때문에 정확한 횟수 대신 대략적인 시간대와 반복 행동을 설명하기를 요청했다. 이 관찰은 `pipeline/search/qualitative_count_ranges.json`에 검토 구간으로 기록했다. 기존 모델의 확정 전환 2건을 사용자 검토의 정확한 총횟수로 바꾸지 않았고 DB의 `0065` 이벤트도 수정하지 않았다.

현재 브랜치에서 `강아지가 소파에 몇 번 올라갔어?`와 `쇼파에 몇 번 올라갔어?`를 실제 DB 이벤트로 실행하면 “영상 시작부터 20초 무렵까지 소파를 여러 차례 빠르게 오르내렸고 정확한 횟수는 확인하기 어렵다”는 취지의 답변과 **0~20초 재생 카드 1개**를 반환한다. `aggregate_result`는 `null`로 두어 UI가 추정 횟수를 숫자 배지로 표시하지 않는다. 다른 영상에는 이 검토 구간을 적용하지 않고, 날짜·시간 필터가 있으면 근거 부족으로 답한다. 전체 280개 테스트가 통과했다. 이 브랜치 코드는 아직 메인·스테이징에 배포되지 않았다.
