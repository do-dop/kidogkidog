# 영상 직접 입력 행동 추출 설계 (초안, 2026-11-19)

상태: 1차 구현됨(`pipeline/events/video_event_extractor.py`, `pipeline/tasks.py` 연결). 기본값 `frames`라 배포해도 동작은 그대로다.

구현 메모
- 환경변수: `BEHAVIOR_EVENT_SOURCE`(frames/video/both), `VIDEO_EVENT_MODEL`(기본 gemini-3.5-flash), `VIDEO_EVENT_INLINE_MAX_BYTES`(기본 12MB, 넘으면 Files API), `VIDEO_EVENT_SHADOW_DIR`(both 모드 결과 저장 위치).
- 주체 일반화("반려동물")는 유지하고 종·외형은 `evidence`의 "상세:" 줄에 남긴다.
- 이벤트 구간 안에 색인 프레임이 없으면(근거 프레임을 못 잡으면) 2초 이내 가장 가까운 프레임까지 구간을 넓힌다. 그보다 멀면 이벤트를 버린다.
- 실제 호출 확인: smartbench_0142(inline, 이벤트 7개, 18초), smartbench_0642(Files API, 이벤트 5개, 35초). 정확도 비교는 아직 하지 않았다(검증 계획 2·3단계).
- 알려진 문제: 프롬프트가 감정 표현을 금지했는데도 "맛있게", "신나게" 같은 표현과 "소리나 기척을 확인하는 듯" 같은 추측이 섞였다.

## 1. 목적

- 행동 이벤트 추출 단계에서 "프레임 6장 → gpt-4o-mini" 방식 대신(또는 나란히) "청크 영상 → Gemini" 방식을 선택해서 쓸 수 있게 한다.
- 근거: 같은 클립 6개(정답 27개)에서 프레임 방식 엄격 재현율 8/27(30%), Gemini 영상 직접 21~24/27(78~89%). 한계는 `experiments/direct-vs-frames-2026-11-19/REPORT.md`에 있다(판정자 차이, 클립 6개, 14~34초 클립).
- 비목표: 프레임 추출, YOLO, CLIP 색인, 검색 순위, DB 스키마(1차)는 바꾸지 않는다. 장면 변화 비교(`scene_change_detector`)도 그대로 둔다.

## 2. 현재 흐름과 바뀌는 곳

```
청크 다운로드 → 프레임 추출 → [GCS 업로드, YOLO, CLIP] → extract_behavior_events → MySQL 저장
                                                       ↑ 여기만 선택 가능하게 한다
```

`pipeline/tasks.py`의 5단계(`extract_behavior_events(indexed_frames=..., video_id=..., limit=20)`)가 유일한 접점이다. 청크 로컬 파일 `local_path`가 이 시점에 이미 있다.

## 3. 설계

### 3.1 선택 스위치
환경변수 `BEHAVIOR_EVENT_SOURCE`
- `frames`(기본): 현재 동작. 배포해도 아무것도 바뀌지 않는다.
- `video`: 영상 직접 입력만 사용. 호출이 실패하면 `frames`로 대체(아래 3.4).
- `both`: 둘 다 돌려 DB에는 `frames` 결과를 저장하고 `video` 결과는 로그와 별도 파일로만 남긴다(섀도 모드). 서비스 영향 없이 스테이징에서 비교하는 용도.

### 3.2 새 모듈 `pipeline/events/video_event_extractor.py`
- `extract_video_events(video_path, indexed_frames, video_id, limit)`를 제공하고, 반환 형태는 `extract_behavior_events`와 같은 이벤트 dict 목록이다. 그래서 하류 코드(저장, 검색)는 그대로다.
- Gemini REST를 `httpx`로 호출한다. `scene_change_detector.py`와 같은 방식(헤더로 키 전달, 실패 시 None)이며 새 의존성이 없다(`httpx`는 이미 있고 `google-genai`는 requirements에 없다).
- 영상 전달: 청크가 작으면(요청 한도 안) `inline_data`로, 크면 Files API로 올린 뒤 삭제한다. 60초 청크는 수 MB라 inline으로 충분할 것으로 보이나 실제 크기 확인이 필요하다.
- 모델은 `VIDEO_EVENT_MODEL`로 지정한다. 모델명이 이전 실험에서 바뀐 적이 있어(2.5-flash는 신규 사용자에게 제공되지 않음) 코드에 고정하지 않는다.
- 프롬프트: 이전 실험의 v2(합치지 말고 나눠라, 빠짐없이)를 출발점으로 하되, 서비스 규칙(반려동물 일반화, 해요체 summary, action_type, continues_previous)을 맞춘다. 정답을 프롬프트에 넣지 않는다.

### 3.3 기존 이벤트 형태로 맞추기
`_normalize_behavior_event(event, group, representative_frames)`를 재사용한다.
- `group`: 청크의 모든 `indexed_frames`(시각 순). 이벤트 시간이 청크 범위로 잘린다.
- `representative_frames`: 각 이벤트의 `[start, end]`에 가장 가까운 색인 프레임 최대 6장. 근거 이미지(`source_frames_json`)와 검색 연결이 그대로 동작한다.
- `evidence`: 모델이 준 `evidence_description`을 "시각: 설명" 형식으로 변환한다.
- 이벤트 상한 `limit=20`, 중복 제거, 흥미도 정렬은 기존 코드를 쓴다.

### 3.4 실패 처리
- 키 없음, 429/5xx(1회 재시도), 파싱 실패, 빈 응답은 예외를 내지 않고 `frames` 경로로 대체한다. 전체 청크 처리가 이 단계 때문에 실패하면 안 된다(`scene_change_detector`와 같은 원칙).
- 모든 호출에 타임아웃을 둔다. 지연이 크게 흔들렸던 이전 측정을 고려해 상한을 정한다(값은 스테이징에서 정한다).
- 처리 상태 기록(PR #65)에 어느 경로를 썼는지, 대체가 일어났는지 남긴다.

### 3.5 이벤트 설명을 더 상세하게
"반려동물이 ~함" 수준에 머무는 것은 모델의 한계가 아니라 프롬프트와 후처리가 정한 것이다.
- 현재 원인: 프롬프트가 주체를 항상 "반려동물"로 쓰라고 하고(`_generalize_subject_prefix`가 문장 앞 주어를 강제로 치환), 한 문장 해요체로 제한하고, 6장만 본다.
- 설계: 영상 경로에서는 기존 필드를 유지하되 한 번의 호출에서 상세 필드를 더 받는다: `appearance`(털색·크기), `count`(보이는 개체 수), `location`(소파 위, 그릇 옆 등), `direction`(이동 방향), `objects`(상호작용한 물건).
- 저장: 1차는 DB 스키마를 바꾸지 않고 `summary`에 상세 문장을 쓰고 상세 필드는 `evidence_json`에 함께 넣는다. 화면과 검색에서 쓸 필요가 확인되면 2차에서 컬럼을 추가한다.
- 정책 결정이 필요한 것: "반려동물"로 일반화하는 규칙을 영상 경로에서도 유지할지(화면에서 종 이름을 쓰지 않는 서비스 정책으로 보인다). 유지하면 종은 상세 필드(`appearance`)에만 남긴다.
- 위험: 상세할수록 환각 가능성이 커진다. 이전 실험에서 행동 주체 오류와 종료 화면 이벤트 환각이 있었다. 상세 필드는 "보이는 것만" 규칙과 근거 시각 요구를 유지하고, 정확도는 같은 정답 세트에서 다시 재서 확인한다.

## 4. 비용과 시간 (확인 필요)
- 이전 실험에서 영상 직접 입력은 입력 토큰이 프레임 방식보다 적었다(영상 1,103~5,380 토큰, 프레임은 이미지 1장당 약 14.6k). 단가는 확인하지 못해 금액은 계산하지 않았다.
- 응답 시간은 재시도 대기가 섞여 신뢰할 수 없다. 스테이징에서 청크당 지연 분포(p50, p95)를 새로 재야 한다.
- 청크 길이를 바꾸면(60초→300초 등) 호출 단위가 바뀐다. `CHUNK_SECONDS`와 함께 봐야 한다.

## 5. 개인정보와 약관
- 영상이 Google로 전송된다. 지금까지는 공개 데이터셋 클립만 사용했다. 실제 사용자 펫캠 영상에는 사용자 동의, 전송 범위, 보관(Files API 업로드 후 삭제), 약관 검토가 필요하다.
- 따라서 기본값은 `frames`이고, `video`는 스테이징·내부 영상에서만 먼저 켠다.

## 6. 검증 계획
1. 로컬: 6개 클립(정답 27)에서 새 모듈 출력이 기존 이벤트 형태·시간 범위·근거 프레임 규칙을 지키는지 단위 테스트(HTTP 호출은 모의).
2. 같은 6개 클립에서 `frames`와 `video` 재현율·정밀도를 가린 판정으로 다시 비교한다(이전 비교의 판정자 차이 제거).
3. 스테이징 섀도 모드(`both`): 실제 청크 수십 개에서 `video` 결과를 저장하지 않고 수집해 이벤트 수, 지연, 실패율을 본다.
4. 기준 통과 시 `video`를 일부 영상에서 켠다. 기준은 사전에 정한다: 엄격 재현율이 `frames`보다 높고, 근거 없는 이벤트 비율이 허용 범위이며, 실패 대체율과 p95 지연이 상한 이내.

## 7. 열린 질문
- 모델과 단가: 어떤 Gemini 모델을 쓰고, 한 달 비용 상한은 얼마인가.
- 청크 길이: 60초 유지인지 5분인지에 따라 영상 길이와 이벤트 수 상한(`limit=20`)이 달라진다.
- 상세 필드를 화면과 검색에 쓸 것인가(2차 스키마 변경 여부).
- 사용자 영상의 외부 전송 허용 범위.
